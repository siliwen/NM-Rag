# 非遗数字人讲解员 · 编排层与 RAG 服务

自研的「胶水层」：把 RAG 检索、会话编排、TTS、渲染串成一条数字人讲解链路。
本机无独立显卡也能完整跑通 RAG 全链路（CPU 语义向量 + 第三方 LLM），渲染环节等 GPU 到位再接。

## 目录

├── config.py            配置（环境变量 / .env）
├── api.py               FastAPI 接口

│   ├── audio.py         音频转写：PyAV 解码 + FunASR 句级时间戳 + 波形静音切块

## 检索质量评测（这是判断「能不能用」的唯一依据）

靠人随便问几句看不出问题，所以做了固定评测集：30 张卡片、33 道题，分五档。

| 档位 | 含义 | 数量 |
|---|---|---|
| L1 | 字面匹配，问题里带专名 | 5 |
| L2 | 同义改写，观众口语提法 | 15 |
| L3 | 跨段推理，需要关联概念 | 6 |
| L4 | 完全越界（食堂几点开门） | 4 |
| L5 | 话题相关但库中无此事实（票价、场次、人名） | 3 |

**L4 与 L5 都不计入命中率**，但要分开看：L4 考「该不该召回」，L5 考「召回到相关内容后由大模型承认资料里没有」。

实测对比（本机 CPU，2026-11-05）：

| 向量模型 | hit@1 | hit@3 | MRR | 检索耗时 |
|---|---|---|---|---|
| `hash` 测试桩（字符哈希） | 76.9% | 80.8% | 0.788 | 6 ms |
| **`bge-small-zh-v1.5`** | **84.6%** | **96.2%** | **0.904** | 18 ms |

`hash` 桩在 L2 档会硬错：「影子戏打哪朝开始的」本该命中「皮影戏·源流」，它匹到「皮影制皮」；
换语义模型后同一题正确命中。**所以不要用 hash 桩判断检索好坏。**

改代码后想确认没退化，跑一次：

```bash
.venv\Scripts\python.exe scripts\eval_retrieval.py --compare   # 桩 vs 语义模型对照
```

## 核心接口

| 接口 | 说明 |
|---|---|
| `POST /knowledge/index` | 文本入库（自动切块），返回卡片数与 id |
| `POST /knowledge/index-pdf` | **上传 PDF 入库**（文本层优先，扫描页自动 OCR，逐页带页码） |
| `POST /knowledge/index-audio` | **上传录音入库**（VAD 切句 + 标点 + 句级时间戳；可传人工校对稿，此时完全不跑识别） |
| `POST /knowledge/seed` | 灌入 `data/corpus` 示例语料；`reset=true` 先清库 |
| `POST /knowledge/search` | 检索调试，返回分数构成（vector / keyword） |
| `POST /knowledge/purge` | 按来源前缀删卡片，删完自动重建 BM25 索引 |
| `POST /eval/run` | 跑评测集，返回 hit@1 / hit@3 / MRR / 分档命中率 |
| `POST /session` | 创建会话 |
| `POST /session/{id}/say` | 发一句话，返回 NDJSON 事件流 |
| `POST /session/{id}/interrupt` | 打断（300ms 内生效） |

事件类型：`state` / `sources` / `token` / `audio` / `done` / `interrupted`

### 关键词权重为什么是自动的

实测扫描（bge-small-zh，30 张卡片 / 30 道题）：

| 关键词权重 | hit@1 | hit@3 | MRR |
|---|---|---|---|
| **0.0（纯向量）** | **88.5%** | 96.2% | **0.923** |
| 0.2 | 84.6% | 96.2% | 0.904 |
| 0.4 | 84.6% | 96.2% | 0.897 |
| 0.6 | 80.8% | 92.3% | 0.865 |
| 0.8 | 80.8% | 92.3% | 0.859 |

有语义模型时关键词是干扰项；但 `hash` 桩没有语义能力，此时关键词是唯一依靠。
所以按能力自动切换（0.2 / 0.6），而不是写死一个数字。

## LLM 接入与模型实测（2026-11-05）

已接入阿里云百炼（OpenAI 兼容模式）。

| 模型 | 首字延迟 | 总耗时 | 结论 |
|---|---|---|---|
| **qwen-flash** ⭐ | **528 ms** | 878 ms | 当前主力：最快且最便宜 |
| qwen-plus-latest | 509~703 ms | 1769 ms | 复杂问题备选 |
| qwen-max | 609 ms | 1299 ms | 质量优先，成本高 |
| qwen-turbo | — | — | 该密钥返回 **429 限流**，不可用 |

## 持久化（SQLite，默认开启）

卡片与向量落在 `code/data/index/knowledge.db`，进程重启、机器重启都不丢；
把整个 `data/index` 目录拷走就是一份完整索引备份。

| 配置 | 行为 |
|---|---|
| `VECTOR_STORE=sqlite`（默认） | 落盘持久化；检索用 numpy 矩阵乘，万级卡片仍是毫秒响应 |
| `VECTOR_STORE=memory` | 纯内存，重启即丢；测试用（conftest 已强制） |

**三个关键设计（都对应真实踩过的坑）**：

1. **重启后 BM25 索引自动重建**。文档 token 靠 `store.chunks()` 顺序对齐，只恢复向量不重建关键词索引的话，
   向量分还在、关键词分全为 0，检索质量无声退化。`HybridRetriever.__init__` 会调 `rebuild()`。
2. **换向量模型不需要手动删库**。库里记录了向量指纹（模型名 + 维度）；指纹对不上时，
   启动阶段用原文自动重算全部向量。原因是 `hash` 与 `bge-small-zh` **同为 512 维**，
   只比维度根本发现不了换过模型，旧向量会被当成有效数据继续用——程序不报错，结果是垃圾。
3. **来源不明的向量也重算**。老版本建的库没有指纹记录，一律视为不可信，启动时重算。

为什么不用 Chroma：非遗知识库规模是几千到几万张卡片，这个量级的暴力余弦是毫秒级，
引入 chromadb 要多背 onnxruntime / tokenizers 等上百 MB 依赖，交付包和运维面都变大。
`VectorStore` 接口是稳定的，真到百万级再换 Milvus，编排层不用动。

## PDF / 扫描件入库

非遗资料的真实形态是申报书、普查表、油印本、影印文献——**大部分是扫描件，没有文本层**。
不做 OCR 直接把 PDF 读进来，结果是入库一堆空白卡片，而且程序一点都不报错。

```bash
# 批量灌目录（.pdf 走服务端解析，.txt/.md 直接当文本）
.venv\Scripts\python.exe scripts\ingest_docs.py ..\assets\samples\pdf

# 单份扫描件：OCR 开关与精度可调
.venv\Scripts\python.exe scripts\ingest_docs.py 某申报书.pdf --ocr always --dpi 200

# 大文件先探路，只跑前 3 页看识别质量
.venv\Scripts\python.exe scripts\ingest_docs.py 某普查报告.pdf --max-pages 3
```

演示台左栏也能直接拖文件上传，上传区带 OCR 模式下拉框。

### 分层策略

| 情况 | 处理 | 耗时 |
|---|---|---|
| 有文本层（文字版 PDF） | `pypdfium2` 直读，不碰 OCR | ~30 ms/页 |
| 有效字符数 < 30（判定为扫描页） | 渲染成图 → `rapidocr-onnxruntime` 识别 | ~5 s/页（CPU） |
| OCR 依赖没装 | **抛 503 并说明装什么**，绝不静默跳过 | — |
| `ocr=never` 且是扫描页 | 标记为 empty + 返回警告清单 | — |

`min_chars` 阈值按**有效字符数**（中文/字母/数字）算，不用 `len(text)`——
标点、软连字符、页码会把空页算成"有字"，这个细节决定扫描件到底会不会被识别。

### 四个必须处理的坑

1. **中文硬换行**。PDF 文本层是按排版行输出的，一行一句地断。不合并的话切块会把每行切成一张卡片，
   语义全丢。合并规则：行尾是句末标点（。！？；）或下一行有条目符号（一、（一）、1.）才断开，
   否则直接拼接（中文不加空格，英文加空格，行尾连字符去掉）。
2. **页码与页眉**。`- 3 -`、`第 3 页`、`3/17` 会被当正文参与 BM25 打分；
   更隐蔽的是每页重复出现的页眉（文件名水印、单位名），靠"在多页重复出现"判定后删除。
3. **卡片 id 跨页撞车**。逐页切块时若每页从 0 编号，不同页的同位置卡片会算出同一个 id，
   入库时被 store 当成重复**静默丢弃**。所以 id 用全局递增序号。
4. **逐页切 vs 整篇切**。选逐页切：整篇切块时页码要靠字符偏移反推，卡片一旦跨页就说不清出自哪页。
   代价是跨页长段会被切成两块——对"引证"要求高的非遗资料，页码可追溯更重要。

### 为什么不用 PyMuPDF / PaddleOCR

| 候选 | 结论 |
|---|---|
| **PyMuPDF** | ❌ **AGPL-3.0**，交付给高校等于传染整个交付包 |
| `pypdfium2`（选定） | ✅ Apache-2.0 + PDFium/BSD，一个库同时做抽文本和渲染，自带二进制，不依赖系统 poppler |
| `rapidocr-onnxruntime`（选定） | ✅ Apache-2.0，PP-OCR 的 onnx 版，纯 CPU、离线、模型随包分发 |
| PaddleOCR | ⚠️ 效果同样好，但要背 paddlepaddle（Windows + Python 3.13 装不动），交付包体积也更大 |

实测：17 页文字版政府文件 → 8669 字 / 49 张卡片 / 1.5 秒，页码全部正确；
模拟扫描件 2 页 → OCR 识别文本与文本层版本**逐字一致**，10.4 秒。

## 口述史音频转写

非遗的另一半资料是**传承人的口述史录音**——老人讲方言、语速慢、停顿多，
录下来是一两个小时的 wav，不进知识库就永远检索不到。

```bash
# 1) 转写并导出可编辑稿（不需要启动服务）
.venv\Scripts\python.exe scripts\transcribe_audio.py ..\assets\samples\audio\某口述史.wav

# 2) 打开导出的 .transcript.txt 改错字（方言必须改），然后回灌
.venv\Scripts\python.exe scripts\transcribe_audio.py --from-transcript 某口述史.transcript.txt --ingest

# 3) 也可以直接上传给服务端转写（省事，但方言错字只能照收）
.venv\Scripts\python.exe scripts\ingest_docs.py ..\assets\samples\audio --max-seconds 180
```

### 转写稿长什么样

```
# 来源：某口述史.wav
# 时长：02:29　引擎：funasr　段数：46
# 直接用编辑器改错字即可；行首的 [时间戳] 不要删，回灌时靠它恢复时间点。

[00:00] 我叫王守义，今年六十七了，家住陕西华县，就是现在叫渭南市华州区。
[00:09] 我们家唱皮影戏到我这一辈是第四代。
```

刻意用纯文本而不是 JSON：校对的人多半不是程序员，能直接在任何编辑器里改才现实。
`[MM:SS]` 前缀就是回读时恢复时间点的依据，总时长从文件头「# 时长：」读回
（不读回的话，尾段的时长会退化成 0，卡片上写着「12:03 - 12:03」）。

### 切块：为什么不能只看时间差

| 证据 | 单独用的问题 |
|---|---|
| 相邻识别段的时间差 | 标点模型会把跨静音的两句**并成一句**，合并后两段首尾相接，**时间差是 0**。实测段落间明明是 1.5 秒静音，时间差却是 0 |
| 波形静音区间 | 单靠它要另跑一次推理；且阈值固定时，有底噪的录音会被整段判成静音 |

所以两个都用：静音检测用**相对噪声底**（5 分位能量 × 2.5，并封顶在语音能量的 35%），
任一条成立就切开。卡片带 `start_ms`/`end_ms`，溯源显示「文件名 · 03:21」。

### 必须传的参数（踩过的坑）

- **`sentence_timestamp=True`**：不传时 FunASR 只回整段文本 + 词级 `timestamp`，
  **没有 `sentence_info`**。结果看起来"成功"（有 text、不报错），但所有卡片时间戳都退化成 0，
  用户点过去永远跳到开头。
- **`kaldi-native-fbank`**：funasr 1.4.x **没把特征提取后端写进依赖**，只装 funasr
  会在第一次识别时抛 `ImportError: torchaudio is not installed and neither is the
  kaldi-native-fbank fallback backend`。
- **16k 单声道**：不是这个采样率必须显式报错。直接把 44.1k 字节喂进去不会崩，
  算出来是一段听不懂的噪音——属于「不报错的错」。

### 实测（149.7 秒模拟口述史，4 段 18 句 482 字）

| 指标 | 干净音频 | 12dB 白噪声 |
|---|---|---|
| 字准率 | **93.87%**（CER 6.13%） | **92.69%**（CER 7.31%） |
| 时间戳中位误差 | **138 ms** | **162 ms** |
| 切块 | 9 张 | 11 张 |
| 转写耗时（CPU） | **12.1 s**（RTF 0.081） | **11.9 s**（RTF 0.080） |

错例几乎全是同音字：「三岁口」→「三碎口」、「碗碗腔」→「婉婉腔」、
「月琴」→「乐琴」、「上油」→「上游」、「递签子」→「第千子」。
**这就是方言口述史必须人工校对的原因**——这些错字进了知识库，
大模型会当成"传承人原话"讲给观众。

已知限制：一处卡片跨过了话题切换。原因是标点模型把跨静音的两句并成了一句话，
卡片文本本身是连续的；要彻底切开得用词级时间戳重新切分句子，当前没做。

## 已知问题

- ⚠️ **越界问题不能靠检索分数阈值来拦**。实测「食堂几点开门」最高分 0.28~0.44，
  而「口传心授为什么容易失传」这类正常问题是 0.48~0.64，两者区间重叠。
  拒答交给大模型判断（已验证会说「这部分资料里还没有记载」），不设脆弱阈值。
- ⚠️ 检索对「影人怎么才能动起来」这类问题仍会把「皮影戏·表演形式」排在「缀结」前面。
  两段内容都讲“动”，属于语料本身的表述重叠，需要靠重排模型或改卡片措辞解决。
- ⚠️ `bge-small-zh` 是 24M 小模型，语义能力有上限。生产期换 `bge-m3` 后需重跑评测确认提升。

## 设计约定（与 AGENT.md 对齐）

- **NO-006**：任何失败显式抛出（`RuntimeError` / HTTP 4xx-5xx），不静默跳过
- **NO-009**：不引入 EdgeTTS；TTS 只允许本地推理
- **DEC-005**：LLM 是唯一允许联网与付费的环节
- **DEC-006**：ASR 只识别观众普通话
- **DEC-018**：PDF 解析用 `pypdfium2` + `rapidocr-onnxruntime`，**禁止引入 PyMuPDF（AGPL）**
- **DEC-020/021**：音频解码用 PyAV（不依赖系统 ffmpeg）；FunASR 必须传 `sentence_timestamp=True`
- **NO-013**：不把未经校对的方言转写直接当交付语料；识别为空时不得返回成功
- 检索必须混合：纯向量会漏非遗专名，BM25 兜字面匹配（标题也参与打分）
